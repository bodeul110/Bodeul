## 화면과 실제 데이터의 대응

| 피그마 요소 | 앱에서 사용하는 값 | 비고 |
| --- | --- | --- |
| 보호자·대상자 카드 | `ManagerDashboard` 참가자 이름, 없으면 `AppointmentRequest` 스냅샷 | 디자인의 예시 이름·사진을 실제 데이터로 오인하지 않음 |
| 보호자 요청 문구 | `AppointmentRequest.specialNotes` | 빈 값이면 미등록 안내 표시 |
| 상시 복용 약물 | `AppointmentRequest.medicationSummary` | 빈 값이면 직접 확인 안내 표시 |
| 안내사항 체크 | 실제 요청 문구 | 보호자 요청 카드와 같은 원천 |
| 진료 자료 확인 | 일반 안내 문구 | 자료 소지 여부를 앱이 미리 확정하지 않음 |
| 검토 완료 | `CompanionSession.preConsultationConfirmed` | 체크 세 항목은 화면 임시 상태이며, 서버에는 전체 검토 결과만 저장 |
| 다음 단계 | 기존 `advanceCurrentStep` | 서버 진행 판정을 유지하고 검토 완료 뒤에만 활성화 |

## 구현 판단

- `PRE_CONSULTATION` 단계에서만 별도 상단 바, 요청 카드, 세 항목 체크리스트, 하단 완료 CTA를 보여준다. 기존 범용 가이드 카드는 숨긴다.
- 피그마의 예시 혈압약 문구나 보호자 사진을 실제 세션 데이터처럼 넣지 않는다. 피그마의 비어 있는 네 번째 체크 카드도 확정된 기능으로 해석하지 않는다.
- 필수 세 항목을 화면에서 모두 선택한 뒤 `검토 완료`를 누르면 기존 단일 서버 확인 플래그를 기록한다. 완료된 상태에서는 서버 응답에 따라 다음 단계 버튼을 표시한다. 체크별 독립 저장은 계약이 없으므로 하지 않는다.
- 기존 현장 메모 저장은 화면 하단의 접기/펼치기 뒤에 유지한다. 메모가 단계 진행의 필수 조건인 것처럼 표시하지 않는다.
- 이 브랜치는 접수·대기 화면 PR #427 위에 쌓인 독립 작업이다. PR #427 병합 전에는 기준 브랜치 관계를 유지하고, 병합 후 최신 `master`로 재정렬한다.

## 확인과 제한

- `assembleDebug`, `testDebugUnitTest` 성공.
- 체크 세 항목 모두 확인, 입력 불가, 저장 중, 이미 완료된 경우를 단위 테스트로 확인했다.
- SM_S901N 실기기의 임시 디버그 미리보기에서 배지·보호자 카드·체크리스트·하단 CTA 배치를 피그마 렌더와 비교했다. 하단 시스템 탐색 영역에 설명문이 가려지지 않도록 조정했고, 미리보기 진입점은 최종 소스에서 제거했다. 실제 데이터 대신 예시 문구로 레이아웃만 확인했다.
- 실제 매니저 대시보드는 2026-09-15 실기기에서 Core API HTTP 500/503으로 조회에 실패했다. 따라서 실제 문진 준비 세션의 요청 메모·완료 저장·다음 단계 이동은 아직 종단 검증하지 못했다.
