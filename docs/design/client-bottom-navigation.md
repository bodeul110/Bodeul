# 환자·보호자 공통 하단 내비게이션

기준일: 2026-08-28

## 작업 목적

환자와 보호자가 예약별 참여관계에 따라 같은 앱을 사용할 수 있도록 최상위 화면 위치와 용어를 하나로 맞춘다.

## 탭 구성

| 탭 | Android 화면 | 역할 |
| --- | --- | --- |
| 홈 | `MainActivity` | 신청, 진행 현황과 주요 안내 |
| 일정·이력 | `ClientBookingHistoryActivity` | 진행 중·완료·취소 예약 목록과 상세 진입 |
| 동행방 | `CompanionChatActivity` | 현재 매칭 또는 진행 중인 예약의 참여자 채팅 |
| 내 정보 | `ClientProfileActivity` | 로그인 역할과 이름·이메일·연락처 확인 |

앱 진입 시 홈을 선택하고, 각 최상위 화면에서는 현재 탭을 선택 상태로 표시한다. 최종 리포트와 동행 진행 상세는 별도 전역 탭을 만들지 않고 일정·이력의 예약 상세에서 접근한다.

## 선택한 방식

기존 Activity를 유지하고 공통 `BottomNavigationView`, 선택 상태 binder와 top-level router를 연결했다. 홈에서 다른 탭으로 이동할 때는 홈을 back stack에 남기고, 홈이 아닌 최상위 Activity에서 다른 탭으로 이동할 때는 현재 Activity를 종료한다. 따라서 알림 등으로 동행방을 단독 실행한 뒤 홈을 눌러도 뒤로가기로 동행방에 되돌아가지 않는다.

동행방을 탭에서 열 때 Android가 새 권한을 판단하지 않는다. Core API가 현재 사용자에게 반환한 예약 중 `IN_PROGRESS` 상태를 전체 목록에서 먼저 찾고, 없을 때만 `MATCHED`를 선택한다. 예약 목록이 진료일 내림차순이어도 미래 매칭 예약보다 현재 진행 중인 동행을 우선하며, 상세 조회와 채팅 동작은 기존 서버 인가 결과를 그대로 사용한다.

서버가 현재 동행방 대상 예약을 반환하지 않으면 동행방의 빈 상태를 표시한다. 일정이 없을 때 일정·이력 화면도 기존 빈 상태와 예약 신청 진입을 유지한다.

## 대안

- 화면 전체를 Fragment와 단일 NavHost로 한 번에 교체한다.
- 역할별로 서로 다른 하단 탭을 만든다.
- 기존 Activity를 공통 탭으로 연결하고 데이터·인가 계약은 유지한다.

## 선택 이유

현재 MVP에서는 이미 검증된 예약·채팅 Activity와 back stack을 보존하는 세 번째 방식이 변경 범위가 가장 작다. 한 계정이 본인 예약과 보호자 대리 예약을 모두 가질 수 있으므로 계정 역할만으로 앱 구조를 고정하지 않고, 예약별 참여관계는 서버 계약에 맡긴다.

## 권한 경계

- API, PostgreSQL schema, Firebase Rules와 역할 권한을 변경하지 않는다.
- 공용 채팅 Activity를 사용하는 매니저와 관리자에게는 환자·보호자 하단 탭을 표시하지 않는다.
- 예약 목록에 없거나 서버 상세 조회가 거부한 예약을 클라이언트에서 열지 않는다.
- 기술적으로 연결된 환자·보호자 관계를 정보공유 동의로 간주하지 않는다.
- 별도 환자의 동행방 추가 참여와 과거 채팅 전역 탐색은 이번 범위에 포함하지 않는다.

## 리스크와 후속 조건

- Activity 기반 탭 전환은 화면별 인스턴스를 사용하므로 화면 구성이 커지면 단일 NavHost 전환을 다시 검토한다.
- 현재 최상위 동행방은 `IN_PROGRESS`를 우선하고, 진행 중 예약이 없을 때만 `MATCHED`를 선택한다. 완료 후 채팅 열람 정책이 확정되면 일정 상세의 읽기 전용 진입으로 별도 제공한다.
