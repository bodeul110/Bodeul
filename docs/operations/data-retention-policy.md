# 데이터 보관 및 파기 정책

기준일: 2026-09-03

## 적용 원칙

이 문서는 운영 구현에 적용할 기술 기본값이다. 개인정보 보호법은 보유기간 경과나 처리 목적 달성으로 불필요해진 개인정보를 지체 없이 파기하도록 요구한다. 위치정보는 서비스 제공 목적을 달성한 뒤 원본을 계속 보관하지 않는 것을 기본으로 한다.

출시 전 개인정보 처리방침, 위치기반서비스 이용약관과 실제 구현을 국내 법률 전문가 또는 개인정보 보호책임자가 최종 대조해야 한다. 법령상 별도 보존 의무가 확인되면 해당 자료만 일반 업무 데이터와 분리해 보관한다.

## 통일된 정책과 적용 상태

2026-08-30에 일반 정책 답변의 `채팅 7일·첨부 7일·매니저 원본 1년`과 전용 보유기간 문서의 값을 대조했다. 2026-09-01 위치 기능의 제품 목표가 바뀌었지만 현재 검증된 데이터별 파기 계약과 production 게이트는 유지한다.

- 환자 GPS 좌표를 1분 주기로 공유하는 것을 제품 목표로 한다. 이 신규 경로는 아직 구현하지 않았다. 기존 매니저 단말의 1회·연속 위치 경로는 Android와 Core API에서 기본 `OFF`이며, release·production은 `false`로 고정하고 debug·Preview에서만 명시적으로 허용할 수 있다. 환자 위치 경로는 동의·철회·인가·파기 종단 검증 전 production 수집·공유를 계속 `OFF`로 유지한다.
- 채팅 본문은 동행 종료(`CARE_ENDED`) 또는 취소 후 180일, 채팅 첨부는 30일 보관한다.
- 결제 영수증·처방 이미지 같은 동행 증빙 원본도 30일을 목표로 하되, 자동 파기 계약을 구현하고 검증하기 전에는 production 업로드를 활성화하지 않는다.
- 신분증 원본은 저장하지 않는다. 자격 증빙 원본은 심사 완료 후 30일 보관한다.
- 범죄경력과 건강 관련 원본은 적법한 수집 근거와 절차를 확인하기 전 수집하지 않는다.
- 전자상거래법이 적용되는 거래가 생기면 계약·결제·서비스 공급 5년, 소비자 불만·분쟁 3년, 표시·광고 6개월의 최소기록만 일반 원문과 분리한다.

정책값을 정한 것과 production 삭제 apply 승인은 별개다. 개인정보 처리방침, 책임자, 복원·삭제 재적용 검증을 마칠 때까지 정기 apply와 쓰기용 파기 자격 증명은 비활성으로 유지한다. 상세 판정은 [MVP 정책 기본값 결정 경계](../planning/mvp-policy-default-boundary.md)를 따른다.

### 위치

- 환자 GPS 좌표를 1분 주기로 공유하는 것을 제품 목표로 하고 4자리 상봉번호는 사용하지 않는다.
- 앱과 Core API의 기존 경로는 매니저 단말의 1회·연속 위치를 다룬다. 이 legacy 경로는 기본 `OFF`이며 release·production에서는 하드코딩된 `false`를 사용한다. debug·Preview에서만 명시적 opt-in을 허용한다.
- Core API가 `OFF`이면 좌표 조회·기록과 legacy 위치 필드 PATCH를 거부하고, 이미 저장된 위치 필드도 응답에서 마스킹한다. Android도 권한 요청·1회 공유·연속 공유 진입을 노출하거나 시작하지 않는다.
- 이 차단은 기존 경로의 운영 노출을 막는 안전 게이트다. 환자 단말 1분 수집, 동의와 즉시 철회, 보호자별 인가, 종료 즉시 삭제 시도와 24시간 이내 최종 삭제는 별도 미구현 범위이며 이번 변경으로 완료 처리하지 않는다.
- 개발·전환 좌표는 동행 종료(`CARE_ENDED`) 또는 취소 시 즉시 삭제를 목표로 하고 실패·지연 건도 24시간 이내 최종 삭제해야 한다. 현재 `expires_at = 종료 시각 + 24시간`과 일 1회 정리 작업은 실제 삭제가 24시간을 넘을 수 있어 이 상한을 보장하지 못한다.
- 정밀 좌표를 장기 분석, 추천 또는 성과 평가 데이터로 재사용하지 않는다.
- 위치 처리 사실 로그는 좌표 없이 주체, 목적, 시각과 제공 대상만 6개월 보관하는 기술 기준을 둔다. 위치정보법상 기록 의무와 실제 적용 기간은 서비스의 위치정보사업·위치기반서비스 해당 여부와 동의 철회 조건을 출시 전에 대조한다.
- production 위치 공유 활성화는 동의·즉시 철회, 약관, 신고 필요성, 수집·열람 인가, 1분 서버 제한, 서버 모드와 원시 좌표 파기를 하나의 변경으로 종단 검증한다.

### 채팅

- 채팅은 별도 PostgreSQL 행으로 저장하고 예약 또는 동행 세션에 연결한다. 배열 필드로 누적하지 않는다.
- 채팅 본문 180일은 CS와 분쟁 확인을 위한 운영 기본값이다. 마케팅, 모델 학습 또는 장기 통계에 사용하지 않는다.
- 첨부는 건강·처방·신분 관련 정보가 포함될 가능성이 있으므로 본문보다 짧은 30일을 적용한다.
- `CARE_ENDED`부터 배정 매니저의 채팅·첨부·건강정보·위치 조회를 회수한다. 가이드 13에는 완료에 필요한 본인 작성 필드만 제공한다.
- 환자는 보관기간 동안 기존 채팅·첨부를 조회할 수 있다. 보호자는 `CHAT` 동의가 유효한 동안 본문을, `CHAT + ATTACHMENT`가 모두 유효한 동안 첨부를 조회할 수 있다. 관리자는 업무 목적과 감사기록이 있는 경우에만 접근한다.
- 사용자가 삭제를 요청했거나 계정을 탈퇴한 경우 법정 보존 또는 유효한 legal hold가 없는 데이터는 정기 만료일보다 먼저 삭제한다.

### 구조화 건강정보와 최종 리포트

- 예약의 환자 상태, 이동지원과 복약 요약은 건강 관련 민감정보로 보고 동행 종료(`CARE_ENDED`)·취소 후 1년을 적용한다. 세션이 만들어지지 않은 요청은 예약일 후 1년을 fallback으로 사용한다.
- 동행 중 생성한 진료·복약 메모는 구조화 건강정보와 같은 시작점을 사용하고, 최종 리포트는 생성이 끝난 `COMPLETED`·취소 후 1년을 적용한다.
- 1년은 환자·동의받은 보호자의 사후 확인을 위한 개발 구현 후보 상한이다. 계약·결제 5년 기록에 포함하지 않으며 production 보관·삭제 apply는 처리방침·법률 자문 회신 대조와 복원 검증 뒤 승인한다.
- 처방전·영수증·동행사진 원본을 리포트에 복사하지 않고, 필요한 경우 등록 여부와 확인된 구조화 결과만 남긴다.
- 현재 migration과 파기 job에는 이 1년 만료 계약이 없다. 만료 필드, 조회 차단과 삭제 job을 구현·검증하기 전에는 production 보관 자동화가 완료됐다고 표시하지 않는다.

### 매니저 증빙서류

- MVP는 병원동행매니저 교육·자격 또는 간호사·요양보호사 등 해당 직무 자격 증빙 1종만 받는다.
- 신분증 원본 파일은 저장하지 않는다. 신분 확인이 필요하면 대면 또는 외부 본인확인 성공 여부와 시각만 기록한다.
- 범죄경력회보서와 건강진단·감염검사 원본은 적법한 조회·수집 근거와 별도 절차가 확인되기 전 선택 제출도 받지 않는다.
- 파일은 JPEG·PNG·WebP, 문서 종류별 활성 파일 1개, 파일당 10 MiB로 제한한다. 안전한 렌더링 경계가 없는 PDF와 100 MiB 다건 업로드는 허용하지 않는다.
- 자격 증빙 원본은 심사 종료 후 30일 안에 삭제하고 자격 종류, 검증 결과·시각, 유효기간과 감사기록만 유지한다.
- 앱의 legacy 키 `healthCertificate`는 실제 간호사 면허를 뜻한다. 신규 계약에서는 수집 목적이 드러나는 `nursingLicense`로 이관한다.
- Storage object 경로를 공개 URL로 만들지 않으며 관리자 서버의 권한 확인 뒤 제한된 시간의 접근 경로만 제공한다.

## 예외 보관

분쟁, 수사 협조, 법적 의무로 기본 기간을 넘겨야 할 때는 다음을 모두 기록한다.

- 대상 사용자와 데이터 범위
- 보관 근거와 담당 승인자
- 시작일과 만료일
- 접근 가능한 운영자
- 해제 및 실제 파기 일시

기술 기본 legal hold는 최대 180일이다. 더 긴 기간은 적용 법령이나 법률 검토 결과를 함께 남겨야 한다. hold 데이터는 일반 조회와 백필 대상에서 제외한다.

## 구현 기준

1. PostgreSQL 테이블에 `expires_at`, `deleted_at`, 필요한 경우 `legal_hold_until`을 둔다.
2. 만료 정리 job은 매일 실행하고 삭제 건수와 실패 건수만 운영 로그에 남긴다.
3. Storage 삭제와 DB 상태 변경은 재시도 가능한 job으로 처리한다. 매니저 증빙은 Firestore transaction에서 서버 전용 삭제 claim을 먼저 확보하고, claim이 존재하는 동안 참조·심사 상태 변경과 새 원본 업로드를 차단한다. 관리자 웹 심사 transaction도 같은 claim을 확인하며, 향후 legal hold나 참조를 바꾸는 Admin SDK 경로를 추가할 때도 동일 검사를 출시 조건으로 둔다.
4. 파기 job은 dry-run 보고서와 실제 apply 모드를 분리한다.
5. 백업 안의 삭제 데이터는 백업 자체 만료 시점까지 존재할 수 있음을 처리방침에 알린다.
6. 월 1회 만료 예정, 삭제 성공, 실패와 legal hold 건수를 운영 보고서로 확인한다.
7. Firestore 전환 기간에도 같은 기간을 적용하며, PostgreSQL 전환을 이유로 만료 데이터를 백필하지 않는다.

## 검증 기준

- 만료 전 데이터는 역할별 정상 조회되고 만료 후에는 조회되지 않는다.
- 다른 사용자의 위치, 채팅과 첨부에 접근하면 403 또는 동등한 거부 응답을 반환한다.
- Storage 삭제 실패가 DB에서 성공으로 표시되지 않는다.
- legal hold가 있는 레코드는 일반 만료 job에서 제외되고, hold 해제 뒤 다음 job에서 삭제된다.
- 파기 결과에는 원문 개인정보 대신 레코드 ID, 정책 코드와 처리 결과만 남는다.

## 구현 상태 (2026-09-03)

- PostgreSQL 만료 후보 조회, 채팅 본문 비식별화, 위치 원본 삭제, 첨부 claim·재시도 계약은 Flyway V13으로 구현했다.
- PostgreSQL V18은 `CARE_ENDED`부터 위치 24시간, 채팅 첨부 30일, 채팅 본문 180일 만료시각을 기록한다. Firestore 전환 파기 함수는 여전히 `COMPLETED/CANCELED`만 종료로 판단하므로, 전환 데이터의 `CARE_ENDED` 시작점은 별도 보완이 필요하다.
- 매니저 증빙 원본은 심사 후 30일과 `managerDocumentLegalHoldUntil`을 transaction에서 확인한 뒤 `managerDocumentDeletionClaim`을 확보하고 삭제한다. claim이 존재하는 동안 매니저 본인은 증빙 참조·심사 상태를 바꾸거나 새 원본을 업로드할 수 없고, 관리자 웹 심사도 중단된다. 같은 claim의 재시도만 Storage generation 조건부 삭제와 참조 정리를 완료할 수 있다.
- 일일 작업은 기본 dry-run이며 `RETENTION_APPLY_ENABLED=true`인 환경에서만 실제 파기를 수행한다.
- 기존 매니저 단말 위치 경로는 Android와 Core API에서 기본 `OFF`로 닫았다. release·production은 활성화할 수 없고, debug·Preview에서만 명시적 opt-in을 허용한다. Core API `OFF`는 좌표 read/write, legacy 위치 PATCH를 거부하고 저장된 위치 필드를 응답에서 마스킹한다. Core API FCM과 Firestore legacy 위치 알림 Functions도 `OFF`에서 발송하지 않으며 production Functions는 프로젝트 ID 경계로 강제 차단한다.
- 개발 환경의 두 예약 함수는 Supabase CA와 DB URL을 각각 Secret Manager에서 주입하고 서버 인증서 검증을 강제한다.
- 월간 보고는 원문, 사용자 ID, 좌표, Storage 경로 없이 건수와 실패 단계만 기록한다.
- 개발 환경에서 새 Core 중첩 첨부 경로의 PostgreSQL·Storage 격리 fixture APPLY, 메타데이터 비식별화와 legal hold 보존을 확인했다. fixture를 정리한 뒤 정기 apply 플래그를 `false`로 복구했고 최종 dry-run 후보는 0건이다.
- Firestore 전환 문서와 매니저 증빙은 `bodeul-dev`의 고정 합성 문서·객체로 dry-run과 단일 APPLY를 검증했다. 만료 세션의 본문·첨부·위치와 만료 매니저 증빙은 각각 1건 처리됐고, legal hold 대상 4건은 보존됐으며 삭제 실패는 0건이었다.
- 검증 뒤 합성 문서 4개와 Storage 객체 4개를 정리하고 최종 상태가 `ABSENT`인지 다시 확인했다. 정기 apply 플래그와 일반 개발 데이터는 변경하지 않았다.
- 구현과 검증 근거는 [#222 개인정보 자동 파기 구현 기록](../reports/issue-222-data-retention-2026-07-19.md)과 [#222 production 위치 게이트 구현 기록](../reports/issue-222-production-location-gate-2026-09-03.md)에 정리한다.
- production 활성화는 개인정보 처리방침, 위치기반서비스 이용약관, 개인정보 보호책임자 또는 법률 검토가 끝난 뒤 진행한다.
