# 2026-08-28 MVP 임시 정책값 경계 점검

## 작업 목적

미확정 기간·횟수 때문에 MVP 기능 구현이 멈추지 않도록 개발팀의 임시 결정 범위와 별도 승인 범위를 분리한다.

## 선택한 방식

기존 기획 답변은 유지하고, 설정으로 되돌릴 수 있으며 local/dev/preview 합성 데이터에만 영향을 주는 값을 `MVP 임시값`으로 기록해 개발팀이 정하도록 했다. 실제 개인정보·권한·금전·법정 의무에 영향을 주는 값은 production 승인과 분리했다.

## 대안

- 모든 미확정 값을 기획 답변 전까지 구현하지 않는다.
- MVP라는 이유로 모든 기간과 정책을 개발팀이 임의로 확정한다.
- 임시 기술 기본값과 실제 운영 정책을 분리한다.

## 선택 이유

현재 MVP 규모에서는 timeout, 재시도, batch, fixture cleanup 같은 가역적 값까지 매번 기획 결정을 기다리면 기능 검증 속도가 떨어진다. 반대로 실제 사용자 데이터의 보관·삭제나 권한·결제까지 임의 결정하면 법률·보안·운영 위험이 커진다. 따라서 세 번째 방식을 채택했다.

- [데이터 보관 및 파기 정책](../operations/data-retention-policy.md)에 실제 사용자 데이터와 production apply는 위임 대상이 아님을 명시했다.

## 검증

- Notion 페이지를 갱신한 뒤 다시 조회해 반영 내용을 확인했다.
- 저장소 링크와 상대 경로를 확인했고 `git diff --check`에서 이상이 없었다.
- 문서 전용 변경이므로 Android, Core API와 Functions 빌드는 수행하지 않는다.

## 리스크

- 임시값이 사용자 문구나 production 환경에 복사되면 운영 정책으로 오인될 수 있다.
- 하나의 이슈 안에 가역적 구현과 승인 필요 범위가 섞여 있어 부분 진행을 전체 완료로 잘못 판단할 수 있다.
- Notion 답변이 추가로 바뀌면 저장소의 이슈 판정표도 다시 대조해야 한다.

## 남은 범위

- #305부터 구현 PR로 진행하고, 부분 진행 이슈는 승인 범위와 겹치지 않는 하위 작업으로 분리한다.
- 보관기간 충돌, 위치 수집, 매니저 서류, 실제 삭제·결제·권한은 기존 승인 게이트를 유지한다.
