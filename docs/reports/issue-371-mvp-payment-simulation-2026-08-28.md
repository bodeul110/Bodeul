# Issue 371 MVP 결제 시뮬레이션 정리

## 작업 목적

PG 연동 전 MVP 결제 화면이 실제 결제 승인으로 오해되거나 가짜 승인 증적을 저장하는 문제를 제거한다.

## 선택한 방식

- 카드와 간편결제는 화면 흐름만 확인하는 시뮬레이션으로 표시한다.
- 시뮬레이션을 확인한 예약은 `PENDING` 상태로 접수한다.
- 승인번호와 승인시각은 생성하거나 저장하지 않는다.
- 기존 `AUTHORIZED` 데이터 해석 경로는 과거 데이터 호환을 위해 유지한다.
- 현장결제는 기존처럼 `DEFERRED`로 구분한다.

## 대안

- 가짜 승인번호를 유지하고 화면 문구만 바꾸는 방식
- MVP 단계에서 결제 화면 전체를 제거하는 방식
- PG 계약과 결제 정책을 확정한 뒤 실제 결제까지 한 번에 구현하는 방식

## 선택 이유

현재 MVP 규모에서는 예약 화면 흐름을 검증할 필요는 있지만 실제 결제 계약과 승인 처리를 구현할 준비는 끝나지 않았다. 화면과 데이터 모두에서 실제 승인으로 보이는 값을 제거하면 향후 PG 연동 전까지 오해를 줄이면서 기존 예약 흐름은 유지할 수 있다.

## 리스크

- `PENDING`은 향후 실제 결제의 승인 대기 상태와 의미가 겹칠 수 있으므로 PG 연동 시 별도 결제 도메인과 상태 전이를 설계해야 한다.
- 기존 `AUTHORIZED` 데이터는 자동으로 변경하지 않는다.
- 이번 변경은 결제, 취소, 환불, 영수증 발급을 구현하지 않는다.

## 구현한 내용

- 카드·간편결제 화면을 MVP 시뮬레이션으로 명시했다.
- 가짜 `BODEUL-<timestamp>` 승인번호 생성을 제거했다.
- 시뮬레이션 결과는 승인 증적 없이 `PENDING`으로 저장하도록 변경했다.
- 알 수 없는 결제 결과 상태는 예약 접수를 진행하지 않도록 닫힌 방식으로 처리했다.
- 결제 확인 도메인 단위 테스트를 추가했다.

## 변경된 범위

- Android 예약 결제 확인 화면과 표시 문구
- 예약 요청의 결제 확인 도메인 모델
- 결제 확인 도메인 단위 테스트

Core API, PostgreSQL 스키마, Firebase Rules, 실제 결제 서비스 연동은 변경하지 않았다.
