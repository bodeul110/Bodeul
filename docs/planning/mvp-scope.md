## 현재 구현과 최신 MVP 경계

### 1. 계정·역할

- 로그인과 회원가입
- 환자·보호자·매니저 역할 분기
- 권한 안내와 필요 시점 최소 권한 요청
- 매니저 자격 서류 제출, 승인 대기와 심사 결과 확인

### 2. 예약·매칭

- 환자·보호자 예약 생성·조회·수정·취소
- 병원·진료과 검색과 카카오 Local 서버 연동
- 건강·이동 정보와 요청사항 입력
- 관리자 전용 PostgreSQL 배정 함수와 매칭 이후 상태 연결
- 매칭 이후 예약·세션 상태 연결

예약 생성·수정·취소는 Spring Core API가, 현재 매칭 배정은 관리자 Next.js 서버의 PostgreSQL admin-only 함수가 담당한다. 앱은 PostgreSQL이나 Kakao REST API에 직접 연결하지 않는다.

Notion 정책 답변은 관리자 배정 A안을 제시했지만 상세 명세에는 매니저 선착순 수락이 남아 있다. 현재 서버의 관리자 배정을 구현 기준으로 유지하고, 충돌이 해소되기 전 매니저 self-accept를 MVP 기능으로 추가하지 않는다.

### 3. 동행 수행·리포트

- 병원 가이드 데이터 기반 단계 진행
- 현장 메모, 보호자 공유, 수납·약국·복약 상태 기록
- 최종 동행 리포트
- 후기, 정산 확인과 긴급 지원 후속 상태

Figma의 13개 가이드 화면은 목표 화면 구조다. 실제 단계 수는 병원 가이드 데이터로 결정한다.

### 4. 진행 공유의 현재 구현

- 환자·보호자·매니저 세션 채팅
- 읽음 상태와 FCM 보조 알림
- 이미지·PDF 다건 첨부
- 매니저 위치 공유와 최근 위치 이력
- Supabase Realtime private Broadcast와 재연결 snapshot 복구

이 목록은 현재 코드와 개발 검증 범위이며, 그대로 production MVP에 포함된다는 뜻이 아니다.

예약·세션·채팅·읽음·위치·리포트·후속 처리는 PostgreSQL, 세션 첨부 원본은 Firebase Storage에 둔다. 인증 프로필·지원·매니저 서류 심사 메타데이터는 현재 Firestore를 사용하고, 매니저 서류 원본은 Firebase Storage에 둔다. Firestore의 기존 예약·세션 업무 문서는 rollback 비교용 읽기 경계이며 새 Core 업무 쓰기의 원본이 아니다.

현재 채팅은 참여자의 직접 메시지를 저장한다. 동행 단계에서 자동 생성되는 시스템 이벤트형 동행방은 아직 구현되지 않았다.

최신 정책 작업안은 보호자·매니저의 300자 직접 채팅, 환자 직접 참여 제외, `CARE_ENDED` 뒤 읽기 전용, 읽음 표시 제외와 일반 채팅 첨부 제외를 제안한다. 현재 앱에는 환자 참여, 읽음과 이미지·PDF 첨부가 구현돼 있어 제품 목표와 코드가 다르다. 답변 안의 첨부 조건도 서로 충돌하므로, 정책 확정 전 기능을 삭제하거나 운영 완료로 표시하지 않는다.

실시간 GPS와 이동경로 추적은 최신 MVP 기준에서 제외하는 방향이 일치한다. 현재 위치 코드와 파기 경로는 이미 구현돼 있으므로 production에서 활성화하지 않고, 4자리 상봉번호와 상봉 확인 흐름이 확정된 뒤 별도 구현 이슈에서 화면·권한·서버 경계를 정리한다.

## 화면은 있으나 운영 완료가 아닌 범위

- 카드·간편결제의 실제 PG 승인
- 취소 수수료, 환불, 노쇼와 초과 시간 추가 결제
- 매니저 수익금 출금과 계좌 정산
- 환자→보호자 진료정보 공유 동의와 철회
- 운영 보험과 사고 대응 절차
- production Kakao 키, Cloud Run·Vercel 실제 운영 전환

이 항목은 UI나 상태 필드가 있어도 실운영 기능으로 설명하지 않는다.

## 현재 MVP에서 제외

- 진료 녹음과 CLOVA STT
- 외부 AI를 이용한 진료 요약 자동 생성
- OCR 처방전·영수증 인식
- 자동 약품 비교와 상호작용·용량 판단
- 자동 초과 결제와 환불 집행
- 매니저의 의료적 판단·복약지도 기능
- 환자·매니저 실시간 GPS 추적과 이동경로 저장

원본 업로드, 수동 기록과 규칙 기반 표시가 있어도 AI·OCR가 구현됐다는 의미는 아니다.

## 출시 전 게이트

1. 환자→보호자 정보공유 동의와 철회 방식
2. 매니저 업무 범위, 사고보고와 보험
3. 취소·환불·노쇼·초과시간 정책
4. 서로 충돌하는 민감정보 보관기간의 기획 승인과 법률 최종 대조
5. production 인프라, App Check, Kakao 키와 rollback 검증
6. 실제 결제가 범위에 포함되면 PG 계약과 서버 검증

## 운영 원칙

- 제품 범위를 늘리는 결정은 Notion 기준 명세와 GitHub Issue에 함께 남긴다.
- 화면 작업은 Figma node를 지정하되 정책·기술 계약은 별도 문서에서 확인한다.
- 구현 완료는 자동화 검사, 배포 또는 실기기 검증 수준을 함께 기록한다.
- 미결 정책은 [Notion 제품 기준 정합성](notion-product-alignment.md)에서 추적한다.
- 되돌릴 수 있고 local/dev/preview의 합성 데이터에만 영향을 주는 값은 `MVP 임시값`으로 기록하고 구현을 진행한다.
- 실제 사용자 데이터, 권한, 금전, 법정 의무에 영향을 주는 항목은 임시값으로 우회하지 않고 출시 전 게이트를 유지한다.
