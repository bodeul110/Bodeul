# MVP SOS·사고 대응 비활성 경계

기준일: 2026-09-03

## 작업 목적

비의료 동행 C안과 MVP 제외 범위가 확정된 뒤에도 앱과 API에 남아 있던 SOS·자동 연락·사고 기록 경로를 비활성화해 제품 설명과 실제 동작을 일치시킨다.

## 선택한 방식

- Android 사용자 화면의 SOS 카드, 담당 매니저·119 전화, 신규 상태 기록을 제거한다.
- 홈·예약 상세·후기·매니저 이력과 관리자 운영 화면에서 SOS를 신규 동작이나 우선순위로 노출하지 않는다.
- 관리자 긴급 이슈 보고·해결 저장 경로를 제거한다.
- Core API는 값이 비어 있지 않은 신규 `supportEscalationStatus` PATCH를 `409 support_escalation_not_supported`로 거부한다.
- JDBC, Firestore와 Mock 저장소의 신규 SOS 쓰기를 제거한다.
- PostgreSQL·Firestore의 기존 열과 필드, 응답 DTO, 파서는 과거 데이터와 구버전 응답을 위한 legacy 읽기 호환으로 유지한다. 정산이나 후기를 갱신할 때도 기존 SOS 열을 덮어쓰지 않는다.
- 현재 존재하는 `REQUESTED`·`MATCHED` 예약 취소와 정상 동행 종료·완료 흐름은 유지한다.

## 검토한 대안

- 기존 SOS 화면을 두고 안내 문구만 바꾸는 방식
- 기존 필드와 데이터를 즉시 삭제하는 migration
- 이번 작업에서 진행 중 사고 전용 중단 상태와 자동 연락 순서를 함께 추가하는 방식

## 선택 이유

현재 MVP에서는 별도 사고 대응 제품과 운영 책임 기준이 없으므로 실행 가능한 SOS 화면을 유지하면 제공하지 않는 기능을 약속하게 된다. 반대로 저장 열을 즉시 삭제하면 이미 저장된 값과 구버전 응답을 깨뜨릴 수 있다. 따라서 신규 실행과 쓰기만 닫고 기존 데이터는 읽기 호환으로 보존하는 방식이 현재 규모와 전환 위험에 맞다.

## 리스크와 전환 조건

- 과거 SOS 값은 API 응답과 내부 모델에 남지만 현재 사용자·매니저 화면의 후속 완료 판단에는 포함하지 않는다.
- legacy 관리자 알림·감사 이력은 과거 운영 기록 확인을 위해 읽을 수 있으나 신규 긴급 이슈를 생성하거나 상태를 기록할 수 없다.
- 이번 변경은 진행 중 사고를 위한 새 중단 상태를 만들지 않는다. 기존 정상 취소·종료 상태를 사고 상태처럼 설명하지 않는다.
- 실제 사고 대응 기능을 다시 도입할 때는 연락 대상과 순서, 응답시간, 책임자, 보호자 전화번호 노출, 기록 보관, 법률·보험·보상 기준을 먼저 확정하고 새 정책과 구현 이슈로 시작한다.
