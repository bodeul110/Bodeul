# 예약 건강 프로필 화면의 Figma 분리 결정

## 목적

Figma MVP의 `예약신청하기` 노드 `8:520`에 있는 `STEP 02. 건강 정보`를 기존의 긴 예약 폼에서 독립 화면으로 분리한다. 화면만 추가하는 데 그치지 않고 현재 예약 생성·수정 계약에 실제로 저장되는 값과 연결한다.

## 적용 방식

- `BookingHealthProfileActivity`가 건강 상태, 복약 정보, 이동 보조 수준, 매칭 주의사항을 입력받는다.
- `BookingHealthProfileSelection`을 통해 기존 `BookingFormBinder`와 값을 주고받는다.
- 예약 폼에는 요약 카드와 `건강 정보 등록/수정` 진입 버튼을 노출하고, 기존 필드는 폼 상태 보관용으로 유지한다.
- 기존 저장 계약과의 매핑은 다음과 같다.
  - 건강 상태 → `patientConditionSummary`
  - 복약 정보 → `medicationSummary`
  - 이동 보조 수준 → `mobilitySupportCode`
  - 매칭 시 주의사항 → `specialNotes`
- Figma 원본 PNG와 SVG는 `docs/design/assets/booking-health-profile`에 보관하고, SVG의 경로 데이터를 Android VectorDrawable로 변환해 사용한다.

## 검토한 대안

1. 기존 예약 폼 안의 건강 입력란만 스타일을 바꾸는 방식
   - 화면 흐름이 Figma의 독립 STEP 02 구조와 달라 제외했다.
2. Figma에 보이는 모든 필드를 UI에 먼저 추가하는 방식
   - 성년후견개시 여부, 여러 개의 매니저 전달 사항, 별도 위급 연락처는 현재 예약 API에 대응 필드가 없어 저장되지 않는 가짜 입력이 되므로 제외했다.
3. 미지원 필드를 `specialNotes` 한 문자열에 임의로 합치는 방식
   - 서버의 필드 의미를 흐리고 수정 화면에서 안정적으로 복원하기 어려워 제외했다.

## 선택 이유

현재 저장 가능한 데이터만 새 화면과 연결하면 프론트엔드 변경만으로도 생성·수정 동작을 유지할 수 있다. 동시에 추후 API 계약이 확장되면 누락된 Figma 섹션을 독립적으로 추가할 수 있다.

## 위험과 후속 작업

- 이 브랜치는 예약 일정 선택 PR #415를 선행 기준으로 사용한다. 건강 정보 PR은 #415 브랜치를 base로 생성하고, #415 병합 후 base를 최신 `master`로 변경한다.
- 성년후견개시 여부, 복수 매니저 전달 사항, 별도 위급 연락처는 백엔드 계약 확정 전까지 노출하지 않는다.
- 예약 폼 복귀 후 값 유지 여부는 Firebase의 환자 기준선 계정 문서가 준비된 환경에서 전체 흐름으로 다시 확인한다.

## 실기기 검증

- 검증일: 2026-09-13
- 기기: Samsung SM-S901N, 1080 × 2340, 화면 밀도 420 dpi
- 통과 항목
  - 화면 실행 및 Figma 기준 상단 앱 바·히어로·카드·입력 영역 렌더링
  - 긴 화면 스크롤과 고정 앱 바 동작
  - 건강 상태 필수값 누락 시 오류 표시 및 입력란 포커스 이동
  - 이동 보조 수준 단일 선택 상태 반영
  - 하단 주의사항 입력 시 키보드 위로 입력란과 저장 버튼 자동 스크롤
  - 유효한 값 입력 후 결과 반환 및 화면 정상 종료, 크래시 없음
- 전체 예약 화면 자동 진입은 디버그 기준선 계정 `patient@bodeul.app`의 `users` 문서가 없어 로그인 단계에서 중단됐다. 이는 화면 구현 오류가 아니며, 계정 문서가 준비되면 예약 폼 요약 반영까지 재검증한다.
